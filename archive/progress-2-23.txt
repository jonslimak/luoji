Why prior fix failed:
1. Prior fix removed broken key `agent:main:main` from session index and restarted gateway.
2. That only reset active session pointer/state and temporarily removed one bad conversation chain.
3. New sessions later reproduced the same failure pattern.
4. Conclusion: root cause is systemic in transcript/replay handling path, not only one corrupted session entry.

Code-path findings supporting replay hypothesis:
1. Installed versions:
   - `openclaw`: `2026.2.15`
   - `@mariozechner/pi-coding-agent`: `0.52.12`

   - `/Users/luo/.nvm/versions/node/v22.22.0/lib/node_modules/openclaw/node_modules/@mariozechner/pi-ai/dist/providers/openai-responses-shared.js`
3. Relevant behavior in that file:
   - Replays persisted `thinkingSignature` by parsing JSON and pushing a `reasoning` item.
   - Replays `toolCall` blocks as `function_call` items (`id` derived from `toolCall.id` split by `|`).
   - If replayed sequence becomes mismatched, OpenAI returns exactly this 400.
4. Historical note:
   - `@mariozechner/pi-coding-agent/CHANGELOG.md` shows a prior fix for this same OpenAI 400 in aborted-turn replay (`0.49.2`, issue #838), but current observed failures occur even after normal first-turn success, so this appears to be a different/remaining replay edge case.

Current assessment (pre-fix):

- Less likely: OpenAI service outage (pattern is deterministic per session history, and first turns succeed).

## 2026-02-16 Investigation Update (A/B Patch Applied)

Context:
- Continued deep debugging of recurring UI/agent error:
  `400 Item 'rs_...' of type 'reasoning' was provided without its required following item.`
- User flagged `[[reply_to_current]]` as suspicious.

Findings confirmed this session:
1. `[[reply_to_current]]` is a valid OpenClaw reply directive token, not random transcript corruption.
   - Parsed by delivery directive parser in installed OpenClaw dist.
   - It can appear in raw assistant text in UI contexts, but is not the replay-pairing root cause.
2. Transcript policy was sanitizing tool call IDs for OpenAI paths, which is unsafe for OpenAI Responses replay.
   - Policy line (before patch) effectively enabled:
     `sanitizeToolCallIds = isGoogle || isMistral || isAnthropic || isOpenAi`
   - Tool ID sanitizer strips non-alphanumeric characters in strict mode, removing `|`.
3. OpenAI replay converter expects `toolCall.id` to retain `call_id|fc_id` shape.
   - Converter derives `function_call` fields by splitting `toolCall.id` on `|`.
   - If `|` is removed upstream, `function_call.id` becomes undefined while replayed `reasoning` ids are still sent, causing the exact 400 pairing failure.

Local reproducible proof (offline script on persisted transcript):
1. Original tool IDs looked like:
   - `call_...|fc_...`
2. After sanitizer path:
   - `call...fc...` (no `|`, truncated/rewritten)
3. Converted replay payload then had:
   - `function_call.call_id` present
   - `function_call.id` undefined
   This matches OpenAI rejection semantics observed in failing turns.

A/B validation on live target machine:
1. A (before patch):
   - `openclaw agent --session-id abtest-openai-400 ... --message "hello"` returned:
     `400 Item 'rs_00afbdcdb4eac59a00699385e16fac8197a029d3abedc789bb' of type 'reasoning' was provided without its required following item.`
2. Patch applied (local hotfix):
   - changed policy to exclude OpenAI from tool-call-id sanitization:
     `sanitizeToolCallIds = isGoogle || isMistral || isAnthropic`
   - patched files:
     - `/Users/luo/.nvm/versions/node/v22.22.0/lib/node_modules/openclaw/dist/pi-embedded-n26FO9Pa.js`
     - `/Users/luo/.nvm/versions/node/v22.22.0/lib/node_modules/openclaw/dist/pi-embedded-CNutRYOy.js`
     - `/Users/luo/.nvm/versions/node/v22.22.0/lib/node_modules/openclaw/dist/reply-B1AnbNl6.js`
     - `/Users/luo/.nvm/versions/node/v22.22.0/lib/node_modules/openclaw/dist/subagent-registry-kdTa9uwX.js`
     - `/Users/luo/.nvm/versions/node/v22.22.0/lib/node_modules/openclaw/dist/plugin-sdk/reply-BhWxw1_E.js`
   - restarted service: `openclaw gateway restart`
3. B (after patch, same failing session path):
   - same `abtest-openai-400` call succeeded with normal assistant output.
   - follow-up turn also succeeded (`test ok`), no recurrence of reasoning-pairing 400.

Conclusion:
- Root cause is local transcript preprocessing/replay compatibility for OpenAI Responses (not a generic OpenAI outage).
- Disabling OpenAI tool-call-id sanitization resolves the recurring error in this environment.

Operational note:
- This is a local patch inside installed npm package dist files.
- It may be overwritten by future OpenClaw updates/reinstalls and should be tracked for re-apply or upstreamed fix.
